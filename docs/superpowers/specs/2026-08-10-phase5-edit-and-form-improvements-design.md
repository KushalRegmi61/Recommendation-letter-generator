# Phase 5 — Professor Edit/Regenerate + Student-Form Improvements

**Date:** 2026-08-10
**Status:** Approved design, ready for implementation planning
**Branch:** `phase5-edit-and-form-improvements`

## Goal

Let professors reopen and fully edit a student's application after a letter is generated, then
regenerate the letter (optionally with a different template), and polish the student intake form
(self-added subjects, a Back button, "GPA or percentage" flexibility, required deadlines) plus add
deadline filtering and sorting to the professor dashboard.

## Context (current state)

Django project `auth`, single app `home`. Function-based views in `home/views.py`. Templates in the
top-level `/templates/`. Supporting modules: `home/dashboard.py`, `home/filters.py`,
`home/letters.py`, `home/intake.py`, `home/identity.py`, `home/forms.py`. Identity is always
resolved via `current_teacher(request)` / `current_student(request)`, never raw cookies. Satellite
writes use the delete-then-recreate pattern inside `transaction.atomic()`.

Key facts established during exploration:

- **Subjects:** global `Subject` table (`sub_name`); `TeacherInfo.subjects` M2M is the teacher's
  subset; `Application.subjects` is a CSV string of what the student took under this professor. The
  student form fetches the chosen professor's subset via `/getdetails`.
- **Student form:** two steps — `studentform1` (`views.py:486`, `Studentform1.html`) and
  `studentform2` (`views.py:696`, `Studentform2.html`). State is carried only in **hidden fields**;
  there is **no Back navigation**. Step 1 already persists the `Application` (+ `Project`/`Paper`)
  before step 2 renders.
- **GPA/percentage:** `Academics.gpa`, `Academics.final_percentage`, `Academics.tentative_ranking`
  are all `CharField(null=True, blank=True)`. In `Studentform2.html` `gpa` and `final_percentage`
  are HTML-`required`; validation is HTML-only (no server-side check).
- **Generation pipeline:** `make_letter` (`views.py:419`, `formTeacher.html`) reopens *any*
  application (no `is_generated` check) and carries the template picker. `renderCustom`
  (`views.py:1491`, `test2.html`) saves anecdote + qualities and renders the preview.
  `download_letter` (`views.py:1913`) is the **only** place `is_generated` is set True; it stores the
  file and overwrites `generated_template`/`generated_at`. Template swap on regeneration already
  works because `download_letter` re-derives the template from the posted `template_id`.
- **Dashboard has no re-open/edit link** for already-recommended students (`Teacher.html` "Students
  You Have Recommended" table links only to download/re-download).
- **Deadlines:** `University.uni_deadline` (`DateField(null=True, blank=True)`), per-university,
  collected in `Studentform2.html`. Not shown on the dashboard; no deadline filter/sort exists.
- **Filters:** `filters.py` `FILTER_PARAMS = ("department", "country", "college", "q")`;
  `dashboard.py` sorts generated by `-generated_at`.

## Decisions (locked with the user)

1. **Self-added subjects:** free-text into the **shared** `Subject` pool via `get_or_create`
   (case-insensitive lookup to reduce duplicates). Not per-teacher.
2. **Professor edit scope:** the **whole application** is editable (all `Application` + satellite
   fields), not just the letter-relevant subset.
3. **Edit UI:** **inline-editable review page** — turn `formTeacher.html` fields into inputs; save in
   place via a professor-scoped view, then flow into the existing preview → download pipeline. Do
   **not** reuse the student intake views (they have a known POST-identity issue).
4. **Deadline UX:** **filter + sort** on the application's **nearest (min)** `university__uni_deadline`.
5. **Per-university deadline becomes required** on the student form (so filter/sort is reliable).
6. **Back button:** ship the **simple** version — Back re-fills step 1 from the DB; step-2 data typed
   before hitting Back is lost (documented limitation).
7. **Rollout:** one branch, one spec; implemented unit order **A → C → E → B → D** (least coupled
   first, the big inline-edit page last).

## Work units

### Unit A — Teacher self-adds subjects (#1)

**Behavior:** on the subject-management page a teacher can type a subject name they taught and add
it. If no matching `Subject` exists (case-insensitive, trimmed), create it in the shared table, then
add it to the teacher's M2M. Students continue to see this professor's subset unchanged.

**Files:**
- `templates/userDetails.html` — add a free-text input + "Add" button in the `#subjects` area,
  posting to `addSubjects`.
- `home/views.py` `addSubjects` (~1401) — resolve by `Subject.objects.filter(sub_name__iexact=name.strip())`;
  if none, `Subject.objects.create(sub_name=name.strip())`; then `teacher.subjects.add(...)`. Ignore
  blank/whitespace-only input.
- `home/views.py` `deleteSubjects` (~1435) — wrap the unguarded `Subject.objects.get(...)` in
  `try/except Subject.DoesNotExist` (FOLLOW-UPS 3.1) so an unknown name no longer 500s.

**Edge cases:** duplicate add (already in M2M) is a no-op; empty string rejected; leading/trailing
whitespace trimmed; existing pick-from-list flow keeps working.

### Unit B — Back button on the student form (#2)

**Behavior:** on step 2, a **Back** button returns the student to step 1 pre-filled with the data
they already saved. Step-2 entries typed before pressing Back are lost (accepted limitation).

**Files:**
- `templates/Studentform2.html` — add a **Back** button that returns to `studentform1` (POST with a
  `back=1` marker, or a GET the view treats as a resume).
- `home/views.py` `studentform1` (~486) — when resolving `current_student(request)` finds an existing
  non-generated `Application`, **pre-fill** every step-1 input (Application fields + `Project`/`Paper`
  satellites, selected professor, selected subjects). Scope strictly via `current_student`; never
  trust a roll/name from the request body for identity.

**Edge cases:** no in-progress application → render empty as today; already-generated application →
still allow editing via the student path is out of scope (professor edit covers post-generation).

### Unit C — GPA *or* percentage (#3)

**Behavior:** the student (and the professor on the edit page) must supply **at least one** of GPA or
final percentage; either alone is valid; both blank is an error. `tentative_ranking` unchanged.

**Files:**
- `templates/Studentform2.html` — remove `required` from `gpa` and `final_percentage`; add helper
  text ("Enter GPA or percentage — at least one").
- `home/views.py` `studentform2` (~696) — server-side: if both `gpa` and `final_percentage` are
  blank, re-render step 2 with an error message and the user's data preserved; do not save.
- The same rule is enforced on the professor edit-save path (Unit D).

**Edge cases:** whitespace-only counts as blank; one present + one blank saves fine.

### Unit D — Professor inline edit → regenerate → change template (#4/#5/#7)

**Behavior:** from "Students You Have Recommended," the professor clicks **Edit**, lands on the
generation page with the **whole application editable**, changes any fields, previews, and downloads —
which regenerates the letter and (optionally) switches template. All scoped to this professor's own
application.

**Files:**
- `templates/Teacher.html` — add an **Edit** button to each recommended-student row, posting `roll`
  to `make_letter` (same as the pending "Create letter" action).
- `templates/formTeacher.html` — convert the student-data display blocks into editable inputs for the
  full application: personal details, applied level/purpose, universities (repeatable: name/country/
  program/**deadline**), academics (GPA/percentage/ranking), subjects (checkboxes from this
  professor's list), strong/weak points, papers, projects, internship, ECA, plus the existing
  anecdote/quality/template controls and the `contenteditable` letter text.
- `home/views.py` — a **professor-scoped save view** (extend `renderCustom` or add a sibling) that,
  gated by `current_teacher` and scoped to `Application(std__roll_number=roll, professor=<me>)`,
  writes the edited Application + satellites inside `transaction.atomic()` using the existing
  delete-then-recreate pattern, enforces the Unit C "GPA or %" rule, then renders the preview
  (`test2.html`). Download proceeds through the unchanged `download_letter`, which overwrites
  `generated_template`, `generated_at`, and re-sets `is_generated=True` — so template swap on
  regeneration (#7) is already covered.

**Security:** the save view resolves identity from the session (`current_teacher`) and refuses any
application not owned by the requesting professor; it does **not** route through the student intake
views. No new unauthenticated surface.

**Edge cases:** editing must not silently drop satellites (atomic block); a regenerated letter
supersedes the stored file (existing `download_letter` behavior); GET on the save view redirects
(don't fall off the end → 500, cf. FOLLOW-UPS 3.3).

### Unit E — Deadline filter + sort on the dashboard (#6)

**Behavior:** the professor can filter both lists to applications whose **nearest** university
deadline is on/before a chosen date, and sort both lists by nearest upcoming deadline. The nearest
deadline is shown in the recommended table.

**Files:**
- `home/filters.py` — add `"deadline"` to `FILTER_PARAMS`; in `apply_application_filters`, when
  `deadline` is present, filter `university__uni_deadline__lte=<date>` with `.distinct()` (same
  to-many join guard as country/college).
- `home/dashboard.py` — annotate `Min('university__uni_deadline')` (e.g. `nearest_deadline`); support
  an optional `sort=deadline` ordering (nulls last) applied to both pending and generated lists;
  expose `nearest_deadline` per row and the active sort in the context.
- `templates/Teacher.html` — add a `<input type="date">` "deadline before" box and a "sort by
  deadline" control to the existing filter row; render nearest deadline in the recommended table.

**Edge cases:** applications with no universities / null deadlines sort last and are excluded by a
"deadline before" filter; existing filters (department/country/college/q) keep composing; both lists
honor the filter as they do today.

## Out of scope

- Application-level (single) deadline field — deadlines stay per-university.
- Persisting step-2 data across the Back button.
- Per-teacher private subject tables.
- Editing a generated application through the *student* path.
- Rotating the compromised committed secrets (tracked separately in FOLLOW-UPS 1.1).

## Testing strategy

`home/tests.py` (~342 tests) with the `login_as_teacher` / `login_as_student` helpers. Per unit:

- **A:** adding a brand-new subject creates one `Subject` and links it; case-insensitive dedupe (no
  second row for "dbms" when "DBMS" exists); `deleteSubjects` on an unknown name no longer 500s.
- **B:** step 1 pre-fills from a saved in-progress application for the logged-in student; a different
  student's in-progress application is never pre-filled.
- **C:** both blank → error, nothing saved; GPA-only saves; percentage-only saves.
- **D:** Edit reopens a generated application; a professor cannot open/save another professor's
  application; an edit + download updates the stored fields, `generated_template`, `generated_at`,
  and keeps `is_generated=True`; the GPA-or-% rule is enforced on save; GET on the save view
  redirects rather than 500s.
- **E:** "deadline before" filter includes/excludes by nearest deadline; sort orders by nearest
  deadline with nulls last; deadline filter composes with an existing filter.
- Student-form deadline now required: submitting a university with a blank deadline is rejected.

Full suite runs once at final review; each implementer runs only its unit's relevant tests.
